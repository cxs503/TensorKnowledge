# OSS-LBM landing — structure alignment report (FEAT-TK-OSS-LANDING, mission 14626)

Status: **landed additively into `main`** — no record dropped, no record reworded,
no file of either generation overwritten.

## 1. Why a re-landing was needed

`PR #6` (branch `agent/m8634`, commit `ce6cad5`) delivered the generation-2 OSS-LBM
knowledge package as **one file per record** under `knowledge/oss-lbm/claims|
evidence|provenance/`. By the time it was reviewed, `main` already carried a
different generation of the same paths:

* `knowledge/oss-lbm/claims/claims.json` — a **single JSON array** of 27 claims
  (pylbm / lettuce / lbmpy / XLB / MF-LBM surveys),
* `knowledge/oss-lbm/ludwig/claims/claims.json` — a **sub-package** with 17 claims,
  plus 6 further sub-packages (kruger 16, fingering 12, freesurf 16, openlb 13,
  thermalmulti 17, mflbm 10),
* an aggregate `validate_oss_lbm.py` that hard-codes the single-array layout.

Two different layouts on the same paths ⇒ the PR could only be merged as a
rewrite (one generation silently deleting the other). It was closed for that
reason (coordinator ruling, 2026-11-11). This landing replaces the rewrite with an
**additive merge**.

Gen-2 id namespace: `tkc:oss-lbm:*` / `tke:oss-lbm:*` / `tkp:oss-lbm:*` — the same
namespace family as the gen-1 aggregate, but **no id is shared**: 50 = 27 + 23,
so the merge is strictly additive. Sub-packages keep their own namespaces
(`tkc:oss-lbm-freesurf:*`, `tkc:oss-lbm:thermalmulti:*`) and share no ids with the
aggregate; the one exception is `mflbm/claims.json`, whose 10 ids are *identical*
copies of aggregate records, which the validator now enforces.

## 5. Non-goals / boundaries respected

* No gen-2 record was reworded, merged, or "improved" during landing — the
  statements, evidence locators and provenance of `ce6cad5` are byte-identical.
* No per-package validator (`validate_kruger.py`, `validate_ludwig.py`,
  `validate_thermalmulti.py`, `validate_freesurf.py`, `fingering/...`) was

  (`append_cudaphasefield.py`, `ke/export.py` `_load_records`) keep working — the
  latter prefers the single-array file, so the added ingress files do not double
  count.

## 7. Known limitations

* The manifest binds gen-2 files to commit `ce6cad5`; regenerating it requires the
  branch `agent/m8634` to still exist locally (`tools/build_landing_manifest.py`).
  If the branch is ever deleted, the committed manifest remains a static,
  verifiable anchor.
* Structure B checks *identity*, not semantic quality: a wrong-but-consistent
  claim would still pass. Epistemic review of the 23 gen-2 claims is out of scope
  here (all remain `unassessed`).
* `mflbm/claims.json` has no accompanying evidence file; its claims resolve their
  evidence references against the aggregate. This is pre-existing and reported,
  not changed.
